# OIANO StudioOS — Scale Readiness Roadmap

**Phase 2** of the Public-Ready Scale & Account Architecture Audit. Every gap identified in [CURRENT_ARCHITECTURE.md](CURRENT_ARCHITECTURE.md) is ranked here by what actually breaks, at what point it breaks, and how expensive it is to fix — nothing in this document is new investigation; it's risk-ranking of confirmed findings. Still no code changes in this phase.

**Status**: Tier 0 is done except **0.3** — 0.1, 0.2 (+2.3), 0.4, 0.5, 0.6, and 0.7 are all implemented and verified (see the table below for what each actually did). Tier 3.1 is also done. **0.3 is the one remaining launch blocker.** This document is a living tracker, not a static snapshot — update it when you finish something, don't just report it in chat and move on (that's exactly the gap that caused this correction).

## How to read this

Each item states: **what breaks**, **the trigger** (the scale condition or event that exposes it), **blast radius** (who's affected when it fails), and **effort** (S/M/L, rough shape not a estimate in days).

Items are grouped into four tiers:

- **Tier 0 — Launch blockers.** Fix before opening public registration. These aren't scale problems, they're "a real stranger will hit this in week one" problems.
- **Tier 1 — Breaks between ~1,000 and ~10,000 users.** Fine today, fails once the stated burst-registration / concurrent-staff / hundreds-of-records-per-account assumptions become real.
- **Tier 2 — Breaks between ~10,000 and ~100,000 users.** Matters at a scale Oiano isn't at yet, but several of these are cheap to do now and expensive to retrofit later.
- **Tier 3 — Architectural decisions to lock in now.** Not urgent to *build*, but the current schema/design shape actively contradicts a stated scale assumption — deferring the *decision* (not necessarily the build) risks exactly the "rebuild from scratch" outcome the brief says to avoid.

A **sequencing note** follows the tiers: several Tier 1 items share one dependency (Redis), and doing them in the right order avoids doing the same infrastructure setup twice.

## Tier 0 — Launch blockers

| # | Gap | What breaks | Trigger / blast radius | Effort |
|---|---|---|---|---|
| 0.1 | ~~No password reset flow~~ **DONE** | A user who forgets their password has zero self-service recovery. Every instance becomes a support ticket or a permanently locked-out account. | Any real user, week one. Whole-platform support-load risk, not just an edge case — password forgetting is routine, not rare. | **Implemented**: `POST /api/auth/forgot-password` + `/reset-password`, a signed short-lived token (the `notificationStreamTicket` pattern, reused as designed), `ForgotPasswordPage`/`ResetPasswordPage`, generic response regardless of whether the email exists (no enumeration). Verified end-to-end via curl: reset succeeds, reused token correctly rejected, login with the new password works. |
| 0.2 | ~~`Booking` table has zero indexes~~ **DONE** | Booking list queries, Pulse's live aggregates, and the room/time overlap conflict check (runs on *every* booking create and reschedule) all do full or near-full table scans. | Degrades continuously as booking volume grows — not a hard cliff, a slow one that's already partially masked by a manually-raised connection pool. Cheapest, highest-certainty win in this entire audit. | **Implemented**: the three planned composite indexes, bundled with 2.3's four (see below) in one migration. Verified live in Postgres via `pg_indexes`. Found and corrected one thing along the way — `bookings` already had a raw-SQL GiST exclusion constraint preventing room/time overlap that predates this work; the new btree indexes are additive to it, not a replacement. |
| 0.3 | Uploaded files: memory-buffered, no live-verified R2 path, no quota | A real user uploading a real (large) audio file buffers the whole thing in the Node process's memory before it reaches storage; the production storage path itself has never been exercised end-to-end (confirmed by the repo's own `docs/TEST_READY_V1_AUDIT.md`, KI-01). | First real multi-MB upload in production is where this is discovered — worst possible place to find it. Single-request memory spikes also risk taking down the whole process under concurrent uploads. | M. Live-verify the R2 path against real R2 credentials before launch (not a code change, a verification task — needs real R2 credentials, which weren't available in this environment). Switch to presigned direct-to-R2 upload URLs so large files never transit the Node process at all — this also directly helps Tier 1's mobile/slow-connection requirement. **Not started.** |
| 0.4 | ~~No CI/CD at all~~ **DONE** | Every deploy today is unverified — no typecheck, no test run, no build check happens automatically. Combined with zero route/integration test coverage, a broken deploy reaches production users with no gate. | First bad deploy after real users exist. Whole-platform. | **Implemented**: `.github/workflows/ci.yml` — typecheck both apps, run the full test suite, build both apps, on every push/PR to `main`. Found and fixed a real, currently-broken root `npm test` script along the way (stale `test:payments` reference from the retired OianoPayment stack). Verified by running every workflow step locally in order — all green. |
| 0.5 | ~~No error tracking / APM, and `/health` doesn't check the database~~ **DONE** | Nobody finds out something is broken until a user reports it — and the health check that's supposed to catch outages would report "ok" even with Postgres unreachable. | First production incident. Whole-platform — this is the difference between "we saw it in 30 seconds" and "we found out from an angry email." | **Implemented**: `/health` now runs a real `SELECT 1`, returns 503 on failure (verified both directions — live success, and a deliberately-bad connection string proving the failure path). `lib/sentry.ts` wired into the existing single error-logging choke point, off by default, no-op proven by test when `SENTRY_DSN` is unset. **Honest gap**: no real Sentry account/DSN was available to verify actual delivery to a dashboard — the integration is correct and safe, but that last mile needs a real account. |
| 0.6 | ~~`JWT_SECRET` does triple duty (auth signing, MFA challenge signing, and derives the TOTP-at-rest encryption key) with no revocation possible~~ **DONE (secret-split half)** | One leaked secret compromises live sessions *and* every stored admin MFA secret simultaneously, and there is no way to invalidate a token before its 7-day natural expiry — not for a reported compromise, not for a password change, nothing. | Any credential leak, any scale. Severity is fixed regardless of user count, which is exactly why it belongs before launch rather than after. | **Implemented**: independent `MFA_ENCRYPTION_KEY`, hard-required in `env.ts` same as `JWT_SECRET`. The one affected account (the seeded `OIANO_ADMIN`) reset to re-enroll cleanly. Verified with a full live round-trip — enroll, verify, then a second independent login cycle proving the persisted encrypted secret decrypts correctly. **Token revocation (the other half of 0.6) is still not done** — no `token_version` column, no logout-everywhere, still pure stateless JWT until natural expiry. |
| 0.7 | ~~**New finding**: `prisma migrate dev` cannot build a fresh database from migration history at all~~ **DONE** | A fresh database build — a new environment, a CI pipeline, disaster recovery, a second engineer's local setup — cannot be created from migration history today. | Whole-platform blast radius for anyone who ever needs a database built from scratch — which a real CI/CD pipeline (0.4) and any disaster-recovery plan both require. | **Implemented**: squashed all 28 broken historical migrations into one baseline generated directly from `schema.prisma` (confirmed zero drift first), plus two raw-SQL constraints Prisma's schema can't express that a naive squash would have silently dropped (the room/time-overlap `EXCLUDE` constraint, the `admin_audit_logs` immutability triggers) — found by scanning every archived migration, not assumed. Old history preserved in `prisma/migrations_archive_pre_baseline/`, not deleted. Proof: built a completely separate fresh database from only the new baseline, diffed it against the live DB — zero differences. `prisma migrate dev` now runs clean for the first time all session. Also fixed the downstream `db:verify-baseline` script and `docs/DATABASE_BASELINE.md`, which turned out to be the team's own already-drafted (but never finished) plan for this exact fix. |

## Tier 1 — Breaks between ~1,000 and ~10,000 users

| # | Gap | What breaks | Trigger / blast radius | Effort |
|---|---|---|---|---|
| 1.1 | No rate limiting beyond the 4 auth endpoints | Booking creation, file uploads, the SSE ticket endpoint, and every other of the ~140 remaining endpoints have zero abuse protection. "Registration may happen in sudden bursts" is explicitly a stated assumption, but nothing downstream of login is protected at all. | A single scripted actor (malicious or just a broken retry loop in someone's browser tab) can hammer any unprotected endpoint. Whole-platform resource exhaustion risk. | S once a shared rate-limit middleware exists — extend the existing `rateLimit.middleware.ts` to a sane global default, tightened per-route where it matters (uploads, booking creation). |
| 1.2 | Rate limiter and SSE registry are both in-process, per-instance | The moment there's a second API instance (for redundancy or zero-downtime deploys — not even for load), rate limits stop being enforced correctly across instances, and SSE notifications silently stop reaching users whose connection landed on a different instance than the one that triggered the event. | Any horizontal scaling, even for reliability rather than load. This is a correctness bug waiting for infrastructure that doesn't exist yet, not a capacity bug. | M. Needs Redis: as the rate-limiter's shared counter store, and as a pub/sub layer so `broadcastToUser`/`broadcastAll` fan out across every instance, not just the one that received the request. |
| 1.3 | No caching layer anywhere | Every read, including Pulse's live per-request aggregates, hits Postgres directly every time, from every connected client, every poll interval. | "Multiple studios may have several staff members logged in simultaneously" — each one polling/viewing Pulse is an independent full query fan-out today. This is the same root cause as `lib/prisma.ts`'s already-necessary manual pool-size bump. | M–L. Short-TTL caching (Redis, same instance as 1.2) for the highest-fan-out reads first: Pulse aggregates, availability checks. Write-path invalidation, not a full rewrite. |
| 1.4 | `resolveStaffStudio` runs a fresh DB query on every studio-scoped request | Correct, but it's a guaranteed extra round-trip on a large fraction of all authenticated traffic, with no caching and nothing in the JWT to shortcut it. | Compounds directly with concurrent-staff load (same trigger as 1.3). | S once Redis (1.2/1.3) exists — cache the `user_id → studio` lookup with a short TTL, invalidated on staff reassignment. |
| 1.5 | No background job/queue system | There's no reliable way to send the Tier 0.1 reset email with retries, no way to run scheduled cleanup, no way to do anything asynchronously without blocking a request. | Blocks or weakens several other fixes on this list (retention, reliable email) rather than failing on its own. | M. A lightweight job runner — BullMQ (reuses the Redis instance from 1.2) or a Postgres-native option like `graphile-worker` if Redis is deferred — sequenced *before* the items that depend on it (1.6, and eventually digest emails / thumbnailing). |
| 1.6 | No retention or archival for unboundedly-growing tables (`Notification`, `ActivityEvent`, `AdminAuditLog`, `BookingMessage`, `WalletTransaction`) | "Hundreds or thousands of sessions, files, credits, collaborators, projects, notifications, and activity records" per account is a stated assumption — these tables have no TTL, no cascade, no cleanup job of any kind today. | Individually slow-building, but compounds across every account simultaneously — by the time it's *felt*, months of unpruned data already exist. Cheaper to start pruning early than to do a giant one-time cleanup later. | S once 1.5 exists — a scheduled job pruning/archiving `Notification`/`ActivityEvent` past N days is a small, low-risk addition. |
| 1.7 | No structured or request-level logging | Debugging a production incident with real traffic means grepping scattered `console.log` calls with no request correlation for anything short of a 5xx error. | First non-trivial production incident once there's real concurrent traffic to reason about. | S. Swap `console.*` for `pino`, add a lightweight request-logging middleware (the `requestId` infrastructure already exists — this reuses it, doesn't replace it). |
| 1.8 | Frontend: no pagination UI, several unbounded list fetches, no request timeout | List views (bookings, roster) will silently truncate once any account has more records than the fixed `limit` the frontend happens to request — the backend already supports `?page=&limit=`, the frontend just never asks. Separately, a hung request never times out — on a slow connection it just spins forever. | Directly triggered by "each account may eventually contain hundreds or thousands of sessions" and by "mobile and slower internet connections must remain usable" — both are explicit stated assumptions this gap violates today. | M. Wire `useInfiniteQuery`/cursor pagination into the highest-traffic lists first (bookings, roster, notifications); add a sane axios timeout + retry-with-backoff for idempotent GETs. |
| 1.9 | No Dockerfile / containerized deploy | Render's native buildpack works, but nothing guarantees two instances are built identically, which matters the moment 1.2 requires more than one instance to exist. | Same trigger as 1.2 — becomes relevant exactly when horizontal scaling starts, not before. | S. A production Dockerfile, tested once against the existing Render service before it's load-bearing. |

## Tier 2 — Breaks between ~10,000 and ~100,000 users

| # | Gap | What breaks | Trigger / blast radius | Effort |
|---|---|---|---|---|
| 2.1 | No test coverage beyond 2 unit tests, no coverage of routes/controllers at all | Every future change, at this scale, risks a silent regression with no automated net — the cost of a bad deploy scales with user count even though the codebase's test coverage doesn't. | Compounds with every feature added; not a hard trigger, a growing-cost-of-change problem. | M, ongoing. Not "write a full suite" as a single item — start with the highest-blast-radius paths: auth, booking creation + wallet debit, payment webhooks. |
| 2.2 | Bundle isn't fully chunk-optimized (`three`/`@react-three` not isolated into its own vendor chunk) | Larger-than-necessary initial payload for users on the stated "mobile and slower internet connections," specifically for a decorative, non-core feature. | Gradually worse as the bundle grows with more features; worth fixing opportunistically rather than urgently. | S. A `manualChunks` pass in `vite.config.ts`, confirming the 3D component is genuinely lazy and off the critical path. |
| 2.3 | ~~`Notification`/`BookingMessage`/`AvailabilitySlot`/`WalletTransaction` remain unindexed even after Tier 0.2's `Booking` fix~~ **DONE** | Secondary hot paths (notification inbox load, message thread load, wallet ledger reads) degrade the same way `Booking` would have. | Same shape as 0.2, just lower current traffic — worth doing in the same migration pass as 0.2 rather than as a separate later effort, since the cost of doing it is nearly zero either way. | **Implemented**: bundled into the same migration as 0.2, exactly as planned here. All four confirmed live in Postgres. |

## Tier 3 — Architectural decisions to lock in now

These aren't "build this before launch" items. They're "decide this before launch," because the current shape of the data model actively contradicts a stated scale assumption, and every account created under the current shape makes the eventual migration more expensive.

| # | Gap | The contradiction | Why deciding now matters | Effort (decision vs. build) |
|---|---|---|---|---|
| 3.1 | ~~`StudioStaff.user_id` is hard-`@unique` — one staff login can belong to exactly one studio, ever~~ **DONE** | Directly contradicted: "Producers/engineers may collaborate across multiple studios." (Note: `Artist` and `Producer` are *not* studio-locked today — this gap was specific to `STUDIO_ADMIN`/`ENGINEER` accounts via `StudioStaff`.) | **Implemented**: `StudioStaff` is now a real `(user_id, studio_id)` membership (`@@unique([user_id, studio_id])` replacing the old `user_id @unique`), `User.active_studio_id` tracks which membership a request is scoped to, `resolveStaffStudio()` auto-resolves it (zero friction for the ~100% of users with one membership) and falls back cleanly if a membership is removed, and `GET /api/studio/memberships` + `PATCH /api/studio/active` give the API surface a future workspace-switcher UI needs. Verified end-to-end: a second membership can now be created without a constraint violation, switching is enforced (403 if you're not staff at the target studio), and a real studio-scoped route (`/api/admin/analytics`) correctly reflects the newly-active studio. Three call sites that authorized against "the admin's one studio" were updated to check membership against the *specific* studio being accessed instead (`messages.routes.ts`, `project-messages.routes.ts`) or to use the new active-studio resolution (`network-exchange.routes.ts`) — a `STUDIO_ADMIN` staffing two studios can now access either one's data, not just whichever one happens to be active. **Not done**: the full workspace-switcher UI (frontend still assumes one studio); that can ship later against this API surface without another migration. | ~~Decision: S. Build: M–L~~ → Build done, S remaining for the UI. |
| 3.2 | File storage has no per-artist/per-studio quota concept anywhere in the schema | "File storage can become substantially larger than normal application database storage" is stated as an expected, not edge-case, condition — yet there's no field to track usage against, let alone enforce a limit. | Retrofitting a quota system after real files exist means a backfill (computing historical usage) on top of the schema change. Adding a `storage_bytes_used` counter (maintained incrementally on upload/delete) now costs almost nothing and avoids that backfill entirely. | Decision + minimal build: S. Full quota *enforcement* (plans, limits, upgrade prompts) can come later — just start counting now. |
| 3.3 | Single-studio invariant (`SINGLE_STUDIO_MODE`) is enforced at boot, but the schema and some route logic (`OIANO_ADMIN` cross-studio queries) already assume multiple studios exist | The codebase has organically outgrown its own stated invariant in one direction (the DB already models 2 studios) while remaining hard-blocked in another (3.1's per-user lock). This is an inconsistent halfway state, not a clean single-tenant *or* multi-tenant design. | Worth an explicit decision: is Oiano's growth path "one Studio row per customer, many customers" (true multi-tenant SaaS) or "one Studio, period" for the foreseeable future? The stated scale assumptions (thousands of users, multiple studios with concurrent staff) imply the former — if so, `SINGLE_STUDIO_MODE` and its boot-time guard should be explicitly retired as part of the same decision as 3.1, not left as dead-but-enforced code. | Decision: S. This is a naming/intent question more than an engineering one — the technical work is 3.1. |

## Sequencing note

A handful of Tier 1 items (1.2, 1.3, 1.4) all resolve with the same piece of new infrastructure — Redis — and one (1.6) depends on a job runner (1.5) that itself is cheaper to build once Redis already exists (BullMQ over a fresh Postgres-only job system). The efficient order is:

1. Tier 0 first, in any order — these are independent of each other and of everything below.
2. Stand up Redis once, then knock out 1.2 → 1.3 → 1.4 in sequence — each is small on its own once the shared infrastructure exists.
3. Stand up the job runner (1.5) on the same Redis instance, then 1.6.
4. Everything else in each tier is independent and can be done in any order or in parallel.

Tier 3 items are decisions, not scheduled work — the recommendation is to make the call on 3.1/3.3 together (they're really one decision) before Tier 0 ships, specifically so no new accounts are created under the shape that would need migrating later. 3.2 is cheap enough to just do alongside Tier 0 rather than only "decide."
